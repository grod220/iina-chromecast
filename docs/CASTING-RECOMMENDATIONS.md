# Chromecast improvements informed by VLC and Google

Reviewed on 22 October 2026 against the installed IINA Chromecast plugin 0.3.1. The most useful next work is connection/session correctness and more selective compatibility recovery. The largest startup improvement would come from producing playable media incrementally. A custom CAF receiver could unlock device capability queries, diagnostics and a different caption renderer, but is a separate architecture choice, not an SDK update inside IINA.

This is a source/documentation review. The proposed VPN, takeover and newer receiver-feature scenarios have not been reproduced on the test receiver. This research does not establish which CAF/Shaka version is running on that TV.

## Changes that fit the current plugin

| Priority | Change | Practical value and evidence |
| --- | --- | --- |
| 1 | Derive media/subtitle URLs from the actual TV connection | VLC reads the TV socket's local address. The helper currently chooses the route to an internet IP at startup. Using the TV route avoids advertising a VPN or obsolete interface address. [VLC maintenance source](https://code.videolan.org/videolan/vlc/-/blob/d80c4667a32c33bb300bb6a43e0bda3713905e2b/modules/stream_out/chromecast/chromecast_communication.cpp#L54-68). |
| 2 | Bind commands and recovery to the owned receiver/content/media session, and bound socket liveness | VLC filters foreign media sessions, distinguishes takeover and tracks unanswered heartbeats. Our plugin handles some interruption cases, but accepts replacement media-session IDs and can reload after a failed reattach even if someone else's media is active. Add transport/content/session checks and write deadlines; retain bounded reconnect for genuine loss. [Session filtering/takeover](https://code.videolan.org/videolan/vlc/-/blob/d80c4667a32c33bb300bb6a43e0bda3713905e2b/modules/stream_out/chromecast/chromecast_ctrl.cpp#L841-881), [heartbeat timeout](https://code.videolan.org/videolan/vlc/-/blob/d80c4667a32c33bb300bb6a43e0bda3713905e2b/modules/stream_out/chromecast/chromecast_ctrl.cpp#L983-1027). |
| 3 | Distinguish delivery failure from codec failure; use separate audio/video fallback choices | Initial compatibility planning already separates direct/remux/audio/video paths. The current error fallback forces conversion of both tracks. VLC keeps those decisions separate; Google's ERROR reason explicitly includes download/network failures. Preserve compatible streams and avoid expensive re-encoding as a response to an unreachable URL. [VLC fallback](https://code.videolan.org/videolan/vlc/-/blob/d80c4667a32c33bb300bb6a43e0bda3713905e2b/modules/stream_out/chromecast/cast.cpp#L907-925), [Google media messages](https://developers.google.com/cast/docs/media/messages). |
| 4 | Respect receiver status and supported commands | Parse supportedMediaCommands, use the documented metadataType discriminator, distinguish initial LOADING from ordinary IDLE, and treat an explicitly reported zero playbackRate differently from a missing value. The current clock substitutes 1 for 0. This is a source-level correctness gap; no TV clock failure was reproduced. These fields already belong to documented media messages and do not require a custom receiver. [MediaStatus](https://developers.google.com/cast/docs/reference/web_receiver/cast.framework.messages.MediaStatus), [message semantics](https://developers.google.com/cast/docs/media/messages). |

Useful optional features on the existing media protocol are playback-speed control, when advertised as supported, and receiver queues with a modest next-item preload hint. Neither requires adopting an Android-only API. Queueing is additional product work: the helper currently publishes a single active movie and would need to retain and prepare multiple assets safely. Preloading can compete with the current movie for bandwidth. [Playback-rate request](https://developers.google.com/cast/docs/reference/web_receiver/cast.framework.messages.SetPlaybackRateRequestData), [queue preload semantics](https://developers.google.com/cast/docs/reference/web_sender/chrome.cast.media.QueueItem), [preload guidance](https://developers.google.com/cast/docs/web_receiver/core_features).

## Larger performance project: stream during preparation

VLC serves produced media through a bounded FIFO, slows the producer when buffers fill and retains some data for a replacement HTTP fetch. Our helper waits for a complete prepared MP4 before serving it. An incremental path could reduce uncached startup delays and temporary storage, particularly when conversion is required. Keep direct/cached file-range streaming for sources that already work well. [VLC streaming implementation](https://github.com/videolan/vlc/blob/68e73a7b9f07f5a95fa77cb4cc4cac554e22f76d/modules/stream_out/chromecast/cast.cpp#L475-L628).

Google documents HLS and DASH, including fragmented-MP4 HLS. A bounded HLS/fMP4 pipeline is therefore a candidate to prototype with the existing receiver before deciding a custom receiver is necessary. It needs explicit handling of seeking beyond prepared segments, timestamps, subtitles, cancellation and replay. Creating multiple quality variants would add encoding cost; a single rendition can still provide incremental delivery. HEVC must not be put in MPEG-TS for Cast. Simply serving a growing ordinary MP4 is not this design. [Streaming protocols](https://developers.google.com/cast/docs/media/streaming_protocols), [supported media](https://developers.google.com/cast/docs/media).

## What a custom CAF receiver could unlock

A small custom receiver would keep the IINA/Go sender but launch our own registered receiver app instead of the Default Media Receiver. It could:

- Call canDisplayType with codec, dimensions and frame rate, inspect device capabilities, and return results through a custom message channel. This is a stronger basis for compatibility decisions than model-name guesses; results still need actual playback/fallback checks. The newer getDeviceInformation API reports identity and is not a codec probe. [CastReceiverContext](https://developers.google.com/cast/docs/reference/web_receiver/cast.framework.CastReceiverContext).
- Report detailed player errors and playback statistics, making delivery/buffering problems easier to distinguish from decode failures. Tune receiver buffering only after measuring the problem. Some PlaybackConfig properties explicitly do not apply to Shaka; shakaConfig is the relevant configuration seam for Shaka playback. [PlaybackConfig](https://developers.google.com/cast/docs/reference/web_receiver/cast.framework.PlaybackConfig), [PlayerManager](https://developers.google.com/cast/docs/reference/web_receiver/cast.framework.PlayerManager).
- Test Shaka's DOM caption renderer through enableUITextDisplayer. This could provide a route to rounded/padded caption design without burning text into the video. It is a different renderer from the TV's native caption boxes, requires receiver-side work and suitable playback, and Google warns of synchronization/alignment issues, especially on older devices. This does not guarantee the requested geometry on the test receiver. [Caption renderer option](https://developers.google.com/cast/docs/reference/web_receiver/cast.framework.PlaybackConfig#enableUITextDisplayer).

Custom receivers require app registration and hosting. Published receiver pages require HTTPS, but Google explicitly permits media content loaded by that page to remain HTTP; movies can continue to be served locally. Unpublished receiver testing requires device registration. Use Google's hosted SDK rather than self-hosting it. [Registration](https://developers.google.com/cast/docs/registration), [custom receiver setup](https://developers.google.com/cast/docs/web_receiver/basic).

## What “latest” means here

Google's current release notes list Web Receiver 3.0.0156, rollout completed 9 September 2026, with Shaka 4.15.56 and Shaka as the default HLS player. These are receiver-runtime changes; installing a new Go dependency does not activate them or prove the TV is running them. Android Sender 23.0.0 on 19 October deprecates PrecacheManager; it is not a new caching interface to build this macOS plugin around. [Google release notes](https://developers.google.com/cast/docs/release-notes).

Google documents Android, iOS and supported-browser senders. The Web Sender SDK requires HTTPS and a Cast-supported browser. The documentation does not provide an official Go/native-macOS sender or a supported drop-in for IINA's WKWebView. Cast Connect targets a native Android TV receiver app; it is not a replacement Go transport library. [Sender setup](https://developers.google.com/cast/docs/web_sender), [Cast overview](https://developers.google.com/cast/docs/overview).

## Recommendation

First implement the current-plugin reliability and status/error-handling changes, preserving native WebVTT and existing direct/cached playback. Next benchmark an incremental HLS/fMP4 path on this TV. Consider a custom CAF receiver if measured capability/diagnostic needs or the desired caption design justify registration and receiver maintenance. Keep native captions as the default until any alternative renderer has passed real-TV readability and synchronization tests.
